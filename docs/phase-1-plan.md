# 近聊（NearChat）第一阶段整体方案

## 1. 目标

第一阶段交付一个能在局域网内直接使用的中心化聊天工具。重点是核心链路稳定跑通，不实现 P2P、群聊、音视频、互联网穿透、全文检索和复杂审计。

可验收能力：

- 管理员创建、启用和禁用账号。
- 用户通过用户名和密码登录。
- 登录后自动看到系统内其他用户及其实时在线状态。
- 两个用户可以实时发送文本消息。
- 离线用户重新登录后可以看到历史消息和未读消息。
- 用户可以发送图片和普通附件，文件存储在私有 MinIO Bucket。
- Docker Compose 一条命令启动应用、PostgreSQL 和 MinIO。

## 2. 关键边界

“自动扫描局域网用户”定义为：服务端通过 WebSocket 连接维护在线状态，并把在线用户列表推送给客户端。客户端不扫描 IP 或端口。

第一阶段为单服务实例，因此在线状态保存在应用内存中；数据库保存账号、会话、消息和文件元数据。以后扩展为多实例时，再把在线状态和事件广播迁移到 Redis。

附件上传下载由业务服务代理：浏览器不直接接触 MinIO 地址或密钥。该方式实现简单、鉴权明确，代价是大文件会占用应用内存，所以当前默认限制为 500 MB。

## 3. 技术架构

```text
浏览器
  ├── HTTP/JSON：登录、会话、历史消息、上传下载
  └── WebSocket：在线状态、新消息、未读变化
          │
          ▼
    NearChat 单体服务
       ├── PostgreSQL：用户、会话、消息、附件元数据
       └── MinIO：图片和附件对象
```

技术选型：

- 前端：React、TypeScript、Vite、Lucide 图标。
- 后端：Node.js、Express、TypeScript、原生 WebSocket。
- 数据库：PostgreSQL 16。
- 文件服务：MinIO 私有 Bucket。
- 部署：Docker Compose。

## 4. 核心数据模型

- `users`：账号、昵称、密码摘要、角色、启用状态、令牌版本。
- `conversations`：当前只有 `DIRECT` 单聊，使用两个用户 ID 组成唯一键。
- `conversation_members`：会话成员和最后阅读时间。
- `messages`：消息主体、类型、客户端幂等 ID、引用消息、撤回时间与创建时间。
- `attachments`：MinIO 对象键、原始文件名、媒体类型、大小、关联消息。

消息写入使用 `(sender_id, client_message_id)` 唯一约束，客户端网络重试不会产生重复消息；历史记录使用创建时间和消息 ID 组成复合游标，避免同一时间戳下漏读。

## 5. 安全基线

- 密码使用 bcrypt 哈希，服务端不保存明文密码。
- JWT 每次请求都校验用户当前状态与令牌版本。
- 禁用用户时增加令牌版本并断开该用户的 WebSocket。
- 读取消息、发送消息、下载附件都校验会话成员关系。
- MinIO Bucket 保持私有，前端不会获得 MinIO Access Key 或 Secret Key。
- 文件名只作为展示元数据；MinIO 对象键使用服务端生成的 UUID。
- 文本消息由 React 按纯文本渲染，避免注入 HTML。

## 6. 界面方向

参考图中的视觉语言，但使用独立的产品结构：

- 浅灰色应用背景，白色大圆角主工作区。
- 左侧为半透明导航和用户列表，主区域突出当前会话。
- 消息内容控制最大阅读宽度；自己的消息使用浅灰气泡靠右显示。
- 底部输入框为较大的浮动圆角面板，附件入口和发送操作放在同一空间内。
- 使用系统字体、低饱和色和少量紫色强调色。
- 所有按钮按下立即反馈；尊重 `prefers-reduced-motion` 和窄屏布局。
